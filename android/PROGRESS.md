# Android progress

Read this first in every session. A row is "done" only with evidence: the
command that was run and what it printed, or a screenshot path. "Tests pass"
alone is not evidence that a feature works (see the quality rules in
`PLAN.md`, "Bağlayıcı kalite kuralları").

Sources of truth:

- Design: `docs/android/mock/index.html`, its reference images in
  `docs/android/mock/ref/<screen>-<theme>.png` (370 x 824 CSS px), the element
  inventory in `docs/android/mock/inventory/<screen>.json` and the tokens in
  `docs/android/mock/tokens.json`. Regenerate with `tools/mockref`.
- Behaviour: `docs/android/PORTING.md` (desktop code to port, with line
  references) and the desktop Go code itself.
- Font: `fonts/GoogleSans.ttf` (variable, 100-1000), the same file the mock
  uses.

Toolchain (in the home directory, no sudo): JDK 21 at
`~/.local/share/jdks/jdk-21*`, Android SDK at `~/Android/Sdk`, AVD `meiro36`
(android-36, x86_64, google_apis). APKs are built here and installed with
`adb`; they are never committed or published.

## M5: deviations, for the owner

- **Where and how**: downloads live in the app's own files (`files/downloads/<sha256 of source:key>.<ext>` + `index.json`, the desktop's naming and index fields, plus the track's other provider refs); no permission is asked. A track is resolved by the bundled yt-dlp (its own URL cache, network only) and saved as served, in its own container: YouTube in 10 MiB ranges with the desktop's Chrome User-Agent (`audio.Save`). **SoundCloud HLS** (the desktop refuses playlists with "cannot be saved as a download"): the phone joins the playlist's init section and segments in order into one file (`.m4a` for fMP4, `.ts`/`.mp3`/`.aac` otherwise); encrypted playlists are refused. Seen on the emulator for one SoundCloud track (fMP4, played offline); other SoundCloud formats are covered by unit tests only.
- **Queue**: 2 at a time, the rest wait oldest first, 30 minutes each, tracks kept or on their way are skipped (desktop). A track already in the playback cache is copied from there instead of downloaded again (the desktop always downloads). Batches: one per list/album/mix asked for (named after it, its cover) or one per track from the menu; "İniyor" shows "done / total şarkı" (plus "N indirilemedi", "sırada") or, for one track, "artist · %NN" / "sırada". × stops a batch (its kept tracks stay, nothing partial is left), "Hepsini durdur" stops all. ~~The mock's "Wi-Fi bekleniyor" never shows~~: since M6b "Yalnız Wi-Fi'de indir" (on by default) holds every download that has not started while the default network is metered, and the row says "Wi-Fi bekleniyor".
- **Snacks**: "İndirme başladı" (the mock's) when something starts; not in the mock: "“X” zaten indirildi", "“X” zaten iniyor", "“X” içinde indirilecek şarkı yok", "“T” indirilenlerden kaldırıldı", "“T” indirilemedi" / "N şarkı indirilemedi" (a batch that ended with failures; the desktop keeps failed rows with "Retry" instead, the mock has no failed state, so failures are not listed or retried from the tab), "Sıralama: …".
- **Storage summary**: used = downloads + both playback caches; free = the app storage's free bytes (`StatFs`). The mock does not say what the bar's width stands for (its 28/9/5% fit neither the used/free ratio nor the sizes); the app scales it to the downloads plus what both caches may hold (2 × 512 MB), so the cache parts fill as the caches fill. Sizes are 1024-based with one decimal under 10 and a Turkish comma ("9,1 MB", "480 MB"), as the mock writes them.
- **"Sırala"** (no action in the mock): goes round newest first (the desktop's order), by title (Turkish collation), by size, with a snack naming the order; kept while the app runs.
- **Rows** use the mock's songRow with "artist · size" (the desktop also shows the provider and "last listened"; the mock does not). The mock's third row (Nightcall) has no downloaded mark although it is listed as downloaded (`DB.s4.dl` is false); the app marks every downloaded track, and the comparison uses the mock's data. With nothing downloaded or on its way the tab shows the summary and the note only (no empty state in the mock).
- **Removal**: "İndirildi · kaldır" in the track menu deletes at once (no question; the desktop's remove button does not ask either) and the removal is sent as `deleted` (desktop tombstones, 90 days).
- **Playback order** (`findAudio`): downloaded file, then the provider's playback cache, then yt-dlp; a downloaded track's play sets its "last listened" (sent with the downloads). A network change does not restart a track that plays from a file. When the resolve fails and music.youtube.com:443 cannot be reached in 3 s, the error is "offline: this track is not downloaded" (desktop wording, shown nowhere yet: the player has no error surface, M3a open item).
- **Playback cache**: the desktop's 512 MB per provider, least recently used out, complete files only, filled in the background from the URL playback already resolved once a track's audio starts (the desktop's `audioStarted`); the desktop also warms the next track into the cache (`Warmable`): not ported. No settings for the sizes yet (M6). It lives in the app's cache dir, so Android may clear it when space runs low.
- **Cover cache**: Coil's disk cache (250 MB, `cacheDir/covers`), read regardless of the server's cache headers; a download's cover is fetched into it when the download finishes. Covers seen offline: the mini player and the rows of downloaded tracks. The desktop's `internal/artwork` was not read (PORTING.md open question 15).
- **Offline state**: "offline" is Android's default network having the INTERNET capability (ConnectivityManager); the banner shows on Home, Ara, Kütüphane and İndirilenler (the mock's `offlineBanner()` places). Offline the search does not ask the providers and goes straight to this device: the downloads, then the playback caches' metadata (the desktop's `localItems`). **Changed**: the stored lists' tracks are no longer part of the offline results (M4b used them as a stand-in until downloads existed).
- **Sync**: the downloads go in the sync snapshot (`syncSnapshot`): each kept track with `device` = `Build.MODEL`, size, last listened, `updated_at` = the later of downloaded and last listened, and each removal as `deleted`; sent with every sync and right after a download, a removal or a play of a downloaded track (changes close together go once). Each uses the mock's unlinked-artist layout ("Anıl Kaya" row): the YouTube Music logo, the text "YouTube Music sanatçısı" (not in the mock) and the inert link button. The mock's MusicBrainz row ("MusicBrainz · Fransa · elektronik") is built and compared with the mock but nothing feeds it yet. YouTube Music "Profile" channels are not shown as artists.
- **Hepsi** shows at most 8 tracks; the "Şarkılar" chip shows all and loads the next page at the end of the list (the mock fixes no count). Songs and music videos both count as tracks; podcast episodes and podcasts are left out.
- **Filter chips** run YouTube Music's own filter (`params` of its chip, by the English label): Şarkılar = "Songs", Sanatçılar = "Artists", Albümler = "Albums", Listeler = "Featured playlists" (YouTube Music's own lists; "Community playlists" is not offered). SoundCloud is asked only for Hepsi and Şarkılar (desktop rule), and its answer for the same query is reused instead of searched again. Before YouTube Music has answered a chip only narrows what is shown.
- **Provider chips** toggle a provider's rows on and off; the last one on cannot be turned off. Turning YouTube Music off hides artists, albums and lists too (they come only from it). The mock shows only the selected state; the unselected one uses the mock's `.chip` style.
- Tracks the app has no MusicBrainz link for show the link button, as in M4a, so every search row shows it until M6.
- "önizleme" is shown for a SoundCloud-only track whose length is 29-31 s (SoundCloud's preview).
- Song meta is "artists · length" (the byline's linked artists joined ", "); YouTube Music gives no length for most rows of an unfiltered search, so those rows show the artist alone. Songs inside YouTube Music's artist card name no artist; the app credits them with the card's artist (the desktop shows "Song").
- A track is listed once per search even when two result pages carry it (same video id). SoundCloud rows take the largest listed artwork (the desktop leaves SoundCloud rows without a cover).
- Album tile meta drops the kind word: "Album • Daft Punk • 2013" becomes "Daft Punk · 2013". List rows say "YouTube Music listesi".
- No loading or error state is shown while a search runs or when one provider fails (the mock has none); the section simply fills when an answer arrives.
- Both providers failing falls back to the mock's offline note "Ağ yok: sonuçlar bu cihazdan, indirilenlerden ve önbellekten." over matching tracks of the stored lists (downloads and the audio cache come in M5; the desktop searches those).
- "Son aramalar" with no recent searches is hidden (the mock has no empty state). Recent searches: newest first, at most 8, a repeat in any case moves up (desktop `Remember`), stored in SharedPreferences on the device only.
- Search suggestions (`music/get_search_suggestions`) are parsed and tested but not shown: the mock has no suggestion panel.
- The search bar scrolls with the results, as the mock's does (only the top bar stays).
- Key maps were generated with a script that is not in the repo (scratchpad); the maps themselves are in `mock-keys/search*.json`.

Lists are in store order (oldest first); the mock fixes no order.
- Tracks the server knows no MusicBrainz link for show the link button (`unknown`), as the mock does for unmatched tracks. The server never sets a track's status (`PORTING.md`), so until M6 every track of a real list shows it and "eşleşen" counts 0.
- A list's cover is its own picture if it has one, else its first track's picture, else the mock's gradient (hue from the list id); track covers are the track's thumbnail, else the gradient. A SoundCloud track from the server carries no thumbnail unless the desktop pushed one.

- At font scale 1.3 and 320dp the bottom bar labels ("Kütüphane", "İndirilenler") end in an ellipsis (one-line label in the mock's own CSS; the stress rule allows a one-line ellipsis, it is not a failure but a visible truncation).

## Open items from M3a

- Mini player: no error surface (a track that cannot play is skipped, up to 3, and the reason is only in logcat and `PlayerUi.error`); tapping opens the full player since M4f (which has no error surface either).
- A play that is running when the process is killed (swipe away, force stop) is never filed (no `finish`): its history row stays at 0 ms and no event is queued. The desktop has the same hole on a crash; a phone is killed more often. Needs a decision (save progress every N s?).
- yt-dlp is updated in the app once a day before the first resolve (the shipped copy returned `client=ANDROID` URLs that answered 403 for some videos); no manual update or "update yt-dlp" message yet.
- Not built (later milestones): ~~audio cache and downloads in `findAudio`~~ (M5), ~~`networkOnline` offline error~~ (M5) (up-next generation, shuffle and repeat are wired since M4f), queue persistence across process death, Last.fm, loudness, episodes, source fallback (`nextSource`), `networkOnline` offline error.
